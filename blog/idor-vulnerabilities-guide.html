IDOR Vulnerabilities: A Practical Guide to Finding and Fixing Broken Access Control

How Insecure Direct Object Reference bugs happen, how to find them as a tester, and how to close them for good as a developer.

what_is_idor

Insecure Direct Object Reference (IDOR) is one of the most common — and most dangerous — vulnerability classes in web applications today. It happens when an application exposes a direct reference to an internal object, like a database record, file, or account ID, without properly verifying that the person requesting it is actually allowed to access it.

IDOR falls under the broader OWASP category of Broken Access Control, which has consistently ranked as the #1 risk in the OWASP Top 10 in recent years. It's popular with attackers because it's simple to exploit, doesn't require any advanced tooling, and often slips past automated scanners entirely.

the_classic_example

The textbook case is a URL or API request that includes an object ID directly, like this:

GET /api/invoices/4521 HTTP/1.1
Authorization: Bearer <your_token>

If the server returns invoice 4521 without checking whether the currently authenticated user actually owns that invoice, an attacker can simply change the number:

GET /api/invoices/4522 HTTP/1.1
Authorization: Bearer <your_token>

If that returns someone else's invoice, you've found an IDOR. No exploit chain, no injection payload — just an incrementing number and a missing ownership check.

where_idor_hides

IDOR isn't limited to numeric IDs in URLs. In real assessments, it shows up in far more places than testers expect:

  • REST API path parameters — /users/1024/profile
  • Query string parameters — ?account_id=8842
  • Request body fields in POST/PUT/PATCH requests — a hidden user_id field the frontend sets but the backend trusts blindly
  • File download endpoints — /download?file=invoice_2024_08.pdf
  • WebSocket messages and GraphQL query variables — often overlooked because testers focus on REST
  • Cookies and JWT claims — a client-controlled identifier the server should never have trusted in the first place
  • Support/admin panels — internal tools are frequently the weakest-tested part of an app, and often have the most sensitive IDOR exposure

a_testing_methodology

Here's the process I use when hunting for IDOR on an engagement:

1. Map every object reference

Walk through the entire application as an authenticated low-privilege user and record every place an ID, slug, or reference appears — in URLs, request bodies, and response payloads. Burp Suite's site map and a proxy history export make this fast.

2. Create two test accounts

You need at least two accounts at the same privilege level. Perform an action as Account A (create an order, upload a document, send a message) and capture the resulting object ID. Then try to access that same object while authenticated as Account B.

3. Test both read and write paths

Most testers stop at "can I view someone else's data" (IDOR on read). Don't stop there — test whether you can modify or delete another user's object too. Write-path IDOR is often more severe and less frequently checked by developers.

4. Try ID manipulation techniques

  • Incrementing/decrementing numeric IDs
  • Swapping your own ID for another captured one
  • Testing with 0, negative numbers, or very large integers
  • If IDs are UUIDs, check if any endpoint leaks other users' UUIDs elsewhere (comments, shared links, autocomplete responses)
  • Testing the same object reference across different HTTP methods (a GET might be protected but a PATCH on the same endpoint isn't)

5. Don't ignore indirect references

Some applications use "indirect" references, like per-session mapping tables, specifically to prevent IDOR. Check whether that mapping is actually enforced server-side, or whether it can still be bypassed by supplying a raw ID directly.

a_real_pattern_i_look_for

One of the most productive things to test is horizontal privilege escalation via secondary identifiers — for example, an app correctly checks that you own an "order," but the invoice attached to that order is fetched via a separate, unchecked endpoint. Developers frequently secure the primary object and forget the related object hanging off it.

how_developers_should_fix_it

From the defensive side, the fix is conceptually simple, even if it takes discipline to apply everywhere:

  • Never trust a client-supplied ID as sufficient proof of ownership. Every object access must re-verify server-side that the authenticated user is authorized for that specific object.
  • Enforce authorization checks at the data-access layer, not just in UI logic or route middleware — a missed check in one controller shouldn't expose the whole object.
  • Prefer indirect, per-user reference maps (session-scoped tokens instead of raw database IDs) for especially sensitive objects, as a defense-in-depth layer — but never as a replacement for real authorization checks.
  • Apply the same ownership check consistently across every HTTP verb and every endpoint that touches the object, including admin and internal tooling.
  • Log and alert on repeated sequential ID access patterns from a single account — it's a strong signal of active IDOR probing.

example_fix

Vulnerable code (Node/Express, simplified):

app.get('/api/invoices/:id', (req, res) => {
  const invoice = db.getInvoiceById(req.params.id);
  res.json(invoice); // no ownership check
});

Fixed:

app.get('/api/invoices/:id', (req, res) => {
  const invoice = db.getInvoiceById(req.params.id);
  if (!invoice || invoice.userId !== req.user.id) {
    return res.status(404).json({ error: 'Not found' });
  }
  res.json(invoice);
});

Returning a generic 404 instead of a 403 for unauthorized objects is a small but useful detail — it avoids confirming to an attacker that an object with that ID actually exists.

why_it_matters

IDOR is dangerous precisely because it's unglamorous. It doesn't need a clever payload, a bypass technique, or deep knowledge of the target's tech stack — just patience and a willingness to change one number in a request. That's also exactly why it's found so often in the wild, across everything from small startups to major platforms, and why it consistently shows up in bug bounty reports and VDP submissions.

If you're testing an application, IDOR should be one of the first things you check — and if you're building one, ownership checks on every object access should be treated as a non-negotiable baseline, not an afterthought.
