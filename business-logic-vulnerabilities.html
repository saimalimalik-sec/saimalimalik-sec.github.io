Business Logic Vulnerabilities: The Flaws Scanners Can't Find

Why the most damaging bugs in an application are often the ones that never trigger a single alert — and how to start looking for them.

what_makes_this_different

Most vulnerability classes — SQL injection, XSS, IDOR — have a signature. A scanner can look for a pattern: an unescaped input, a missing check, a suspicious string reflected back in a response. Business logic vulnerabilities don't work that way.

A business logic flaw isn't a broken security control — it's a correctly functioning application doing exactly what it was built to do, in a sequence or context nobody anticipated. The code has no bug in the traditional sense. The bug is in the assumptions behind the workflow.

That's exactly why automated scanners consistently miss this entire class of vulnerability — there's no malformed input to detect, no error message to catch. It requires understanding what the application is supposed to do, then finding the gap between that intent and what it actually allows.

a_few_real_patterns

These are generic, commonly seen patterns — not specific to any one engagement or organization:

1. Price and quantity manipulation

A checkout flow calculates the total client-side, then sends it to the server as a parameter the backend trusts without recalculating. Change the price field in the request, and the order goes through at whatever value you set.

2. Race conditions in one-time actions

A "redeem coupon" or "claim reward" endpoint checks "has this been used?" and then marks it as used — as two separate steps. Fire the same request multiple times in rapid succession before the first one finishes writing to the database, and the check passes every time before any of them get marked as redeemed.

3. Workflow step skipping

A multi-step process — say, identity verification before a withdrawal is approved — assumes the user will hit each step's endpoint in order because that's what the UI enforces. But if each step is its own API call with no server-side state tracking "which step are we actually on," you can call step 4's endpoint directly and skip verification entirely.

4. Negative and boundary values

A "transfer funds" feature validates that the amount is a number, but never checks that it's positive. Enter a negative number, and instead of sending money, the operation reverses — often crediting the sender's account instead of debiting it.

5. Trust boundary confusion between roles

An action is properly restricted for a "regular user" role, but a feature added later for a "manager" role reuses old logic that assumed only trusted internal staff would ever reach that code path — and doesn't re-validate what the current user is actually allowed to do.

the_mindset_shift

Testing for technical vulnerabilities asks: "can I break this input?" Testing for business logic asks a different question entirely: "what did the developer assume would always be true, and what happens if it isn't?" That mindset shift is really the entire skill.

a_testing_approach

1. Map the intended flow first

Before touching anything, walk through the feature exactly as intended — as a normal user would. Write down every assumption the flow seems to make: order of steps, who's allowed to do what, what values are expected to stay within range.

2. Attack the assumptions, not the syntax

For each assumption, ask what happens if it's violated:

  • What if I call step 3 before step 1?
  • What if I send this request twice at the exact same moment?
  • What if this "always positive" value is negative, zero, or absurdly large?
  • What if I use a valid session, but for an action that logically shouldn't apply to my role?

3. Test state, not just single requests

Business logic bugs often only appear across a sequence of actions, not in any single request. Use Burp Suite's repeater to replay steps out of order, and its intruder or a simple script to fire concurrent requests for race condition testing.

4. Think about the underlying incentive

Ask: if I were trying to get something for free, skip a required step, or make the system do something financially or operationally wrong — where would I push first? Attackers targeting business logic are usually motivated by a concrete gain (money, access, data), not just curiosity, so reasoning about incentive often reveals where to look.

why_it_belongs_in_every_engagement

Business logic testing doesn't replace technical vulnerability testing — it's a separate pass that has to happen deliberately, because nothing about a standard scan or checklist will surface it on its own. A web application can pass every automated security scan, have no SQL injection, no XSS, properly validated inputs everywhere — and still lose money or leak data because a workflow was designed only for one intended path through it.

This is also why these bugs tend to be some of the highest-severity findings in bug bounty programs: they're rare precisely because they take real thought to find, and their impact — direct financial loss, privilege escalation, data exposure — is often more concrete and easier to demonstrate than a technical bug alone.
